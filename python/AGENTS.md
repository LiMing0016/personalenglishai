# Python 协作规则

本文件定义 `python/` 目录下的通用开发规则，适用于该目录中的所有 Python 代码。

## 作用范围与优先级

1. 本文件是 `python/` 范围内的总规则。
2. 如果子目录（如 `ai_orchestrator/`）存在更细的 `AGENTS.md`，则必须同时遵守。
3. 当总规则与子目录规则冲突时，以子目录规则为准；未覆盖部分继续遵守本文件。
4. 本规则面向本项目的 Python 侧 agent 应用开发，不作为通用平台研发规范。

---

## 当前定位

1. `python/` 目录的主线是业务 agent 应用开发，不是通用 AI 基建研发。
2. 新的 agent 能力默认进入 `ai_orchestrator/`。
3. `context_sidecar/` 视为遗留组件，不再作为新能力主承载点。
4. 除修复故障、兼容存量调用或完成迁移所必需的改动外，不要继续向 `context_sidecar/` 增加新功能。
5. 不要在 `python/` 目录内继续演化新的通用 agent runtime、memory runtime、conversation runtime 或 orchestration framework；该目录下的 agent 开发应聚焦业务应用能力。

---

## 总体架构原则

Python 侧运行单元分为四类，职责必须明确区分：

### 1. orchestrator agent

负责：
- 任务识别与路由
- 上下文装配
- tool 调度
- capability agent 调用
- workflow 编排
- 结果汇总与输出适配

不负责：
- 承载大量业务细节
- 内嵌过多 prompt
- 直接实现具体领域能力

### 2. capability agent

负责单一垂直能力，例如：
- 评分
- 润色
- 词汇讲解
- 翻译反馈
- 句子分析

要求：
- 职责单一
- 输入输出明确
- 可独立回归测试
- 不承担全局规划

### 3. workflow

负责固定业务链路编排，例如：
- 评分后生成反馈
- 评分后再润色再复评
- 单词讲解后生成练习
- 用户提交作文后的完整分析链路

要求：
- 编排顺序清晰
- 中间状态显式
- 适合复用
- 不混入大量底层 I/O 适配逻辑

### 4. tool

负责可复用、结构化、可验证的能力调用，例如：
- 获取 rubric
- 加载用户画像
- 检查字数
- 审题
- 查询词库
- 错误分类
- 保存评估结果

要求：
- 输入输出结构化
- 副作用明确
- 优先无状态
- 可单测

service、schema、adapter、HTTP/CLI 入口等属于支撑层，不替代 agent、workflow、tool 的职责边界。

---

## 新增能力准入规则

新增业务能力时，必须优先按以下顺序判断落位：

1. 优先扩展现有 tool
2. 其次新增 workflow
3. 再考虑新增 capability agent
4. 最后才允许改动 orchestrator agent

只有同时满足以下条件时，才允许新增 capability agent：

1. 需要独立 prompt
2. 需要独立输入输出契约
3. 能被多条 workflow 复用
4. 可以单独做最小回归验证
5. 不适合作为单纯 tool 实现

不符合以上条件的新增需求，不应直接新增 agent。

---

## OpenAI 技术路线

1. Python 侧 agent 开发统一采用 OpenAI 官方能力与工作流。
2. 默认使用 OpenAI Agents SDK，不自行再造一套 agent runtime。
3. 对于记忆、对话管理、上下文编排、tool 调度、handoff、trace 等能力，优先采用 SDK 或官方推荐方案。
4. 非经明确批准，不引入其他 agent 框架。
5. 如果 OpenAI 官方 SDK、官方工作流或推荐模式已经能满足需求，应优先采用，不继续自定义底层替代层。
6. 允许围绕配置、日志、trace、schema 校验、运行入口适配编写轻量封装，但不得扩展为新的 agent runtime 或平台层。
7. 不要为了“统一抽象”而在 SDK 外再包一层同构框架。

---

## 业务对象优先原则

新能力设计应优先围绕明确业务对象展开，而不是抽象出脱离业务的通用 agent 概念。

本项目优先围绕以下业务对象组织能力：

- 用户画像
- 作文题目
- 作文文本
- rubric
- 词汇/表达资源
- 练习记录
- 评分结果
- 润色结果
- 错误标签
- 成长数据

要求：

1. 新的 prompt、tool、workflow、schema 应尽量映射到明确业务对象。
2. 不鼓励新增脱离业务对象的通用抽象 agent。
3. 不要为了“平台感”优先抽象底层，而忽略业务主链路。
4. 设计优先服务当前业务闭环，而不是假设未来无限扩展。

---

## Prompt 与开发风格

1. Prompt 风格必须对齐 OpenAI developer 文档习惯。
2. Prompt 应保持清晰、结构化、约束前置，明确角色、目标、输入、输出和边界。
3. 避免堆砌空泛人设、装饰性语气和不可验证的行为描述。
4. Prompt 是正式资产，不应随意散落在临时脚本、测试代码或 notebook 中。
5. Prompt 正文与元数据可以分层管理，但必须命名清晰、用途明确、便于评审和回归。
6. Prompt 不应与大量业务逻辑、I/O 适配、状态处理混写在一个文件里。
7. 高风险 prompt 变更必须有最小回归样例或 smoke test。
8. Prompt 需要能够被明确定位到所属 agent、workflow 或场景。

---

## 目录与结构原则

1. 项目目录结构应符合主流 agent 应用开发习惯。
2. 目录组织优先服务 agent、tools、workflows、prompts、schemas、services 等应用层能力，而不是围绕临时脚本堆积。
3. 不要把实验代码、一次性脚本、运行产物和正式模块混放。
4. HTTP 入口、CLI 入口或其他对外适配层，应与核心编排逻辑分开。
5. 代码组织应支持“核心编排逻辑可复用，接口层只是适配层”。
6. 不要把 prompt、业务逻辑、I/O 适配、状态管理全部揉进一个文件。
7. 新模块应优先放入现有清晰目录，不要随意新增含义模糊的目录层级。

---

## 依赖管理规则

1. 允许引入服务于 agent 应用开发的常见配套库。
2. 但不要引入新的 agent 框架。
3. 新依赖必须先回答：
   - 是否直接服务当前 agent 应用需求
   - OpenAI 官方 SDK 或现有实现是否已足够
   - 是否引入额外运行时复杂度、维护成本或迁移成本
4. 不要为了抽象 SDK、包装 runtime 或追求“框架感”引入依赖。
5. 能用标准库、现有依赖或 OpenAI 官方能力解决的，不额外加库。
6. 新依赖应优先体现在明确业务需求、验证方式和影响范围中，而不是因为“未来可能有用”。

---

## Tool 设计契约

每个 tool 必须具备清晰契约，不允许随意返回风格各异的数据结构。

### 每个 tool 至少应明确：

1. 输入 schema
2. 输出 schema
3. 是否有副作用
4. 是否幂等
5. 失败行为或异常约定
6. 超时与重试策略（如适用）
7. trace / request_id / 调试上下文的接入方式（如适用）

### 设计要求：

1. tool 优先返回结构化数据，不返回难以消费的自由文本。
2. tool 的业务逻辑与外部适配代码应分离。
3. 可复用能力优先实现为 tool，而不是写进单个 agent prompt 中。
4. tool 不应偷偷依赖隐式全局状态。
5. 有副作用的 tool 必须在命名、文档和调用点上显式可见。

---

## 状态、记忆与上下文规则

1. 对话状态、记忆、上下文编排优先采用 OpenAI 官方能力或推荐模式。
2. 未经批准，不自行实现新的 memory runtime、conversation runtime 或通用上下文系统。
3. 新能力默认保持无状态；确需持久化状态时，必须明确：
   - 状态来源
   - 生命周期
   - 读写边界
   - 一致性要求
   - 验证方式
4. 不允许把新的记忆系统、上下文系统、对话状态系统继续堆在 `context_sidecar/`。
5. 需要沉淀业务结果时，应优先围绕业务对象设计显式存储，而不是隐式塞入上下文黑盒。

---

## 设计与实现原则

1. 优先做小范围、安全、可验证的修改。
2. 除非明确要求，不要顺手扩展成底层平台重构。
3. 优先沉淀可复用的 agent 应用模块，而不是写一次性拼装代码。
4. agent、tool、workflow 的边界必须清晰。
5. 修改前先确认影响范围、调用链路和验证方式。
6. 修改后必须说明哪些验证已运行，哪些未运行。
7. 不要把同一个需求拆成多个相互耦合、边界不清的新模块。
8. 对外接口与核心业务编排应分层，避免入口层侵入核心逻辑。
9. 能复用现有 schema、tool、workflow 时，不重复造同类能力。

---

## 禁止事项

以下做法默认禁止，除非有明确批准：

1. 新增通用 agent runtime、memory runtime、prompt runtime
2. 引入新的 agent 框架
3. 在 `context_sidecar/` 继续堆新能力
4. 让 capability agent 自由互调、相互自治协作
5. 把大量业务规则硬塞进 HTTP/CLI 入口层
6. 把 prompt 散落在脚本、测试、notebook 或临时代码里
7. 在未验证核心链路的情况下宣称“已经可用”
8. 以“未来扩展”为理由进行大范围抽象或平台化重构
9. 用自由文本代替关键结构化输出
10. 不经约束地把路由逻辑、业务逻辑和输出格式化逻辑混在一起

---

## 测试与验证要求

Python 侧改动后，至少应提供可运行验证，不要只靠主观判断。

### 基本要求

1. agent、tool、workflow 改动都应有对应验证。
2. Prompt 改动至少要有最小回归样例或 smoke test。
3. 如果没有运行完整验证，必须明确说明缺口。
4. 不要在未验证核心链路的情况下宣称“已经可用”。

### 建议验证方式

包括但不限于：

- 单元测试
- 最小 smoke test
- 针对关键 prompt 的输入输出回归样例
- 关键 agent/tool/workflow 的端到端调用验证
- schema 校验测试
- 关键异常路径验证

### 最低完成标准

- 改 tool：至少有单元测试或最小调用验证
- 改 workflow：至少有一条端到端 smoke case
- 改 prompt：至少有一组输入输出回归样例
- 改 schema / contract：至少有序列化与校验测试
- 改 orchestrator：至少覆盖主路径和一个失败路径的验证

---

## 交付与说明要求

每次重要改动后，应至少说明：

1. 修改了哪些模块
2. 影响哪些调用链路
3. 新增或调整了哪些 contract / schema / prompt
4. 已运行哪些验证
5. 尚未运行哪些验证
6. 已知风险或待补项是什么

没有完成验证时，不得给出“已完全可用”的表述。

---

## 遗留模块处理

`context_sidecar/` 当前不作为未来 agent 体系的核心方向。

规则如下：

1. 不继续往该目录扩展新能力。
2. 如需修改，优先以修复、兼容、迁移收口为目标。
3. 不要把新的记忆系统、上下文系统、对话状态系统继续堆在该目录上。
4. 后续如有替换路径，应优先向 OpenAI 官方工作流收敛。
5. 对 `context_sidecar/` 的修改应额外说明：
   - 修改原因
   - 与迁移路径的关系
   - 是否增加了后续迁移成本

---

## 文档要求

涉及以下变化时，应检查是否需要同步更新文档：

- agent 架构
- tool 边界
- workflow 设计
- prompt 组织方式
- 接口契约
- 运行方式
- 配置项
- 部署方式
- 数据流或状态流

规则：

1. 如果变更会影响团队后续 agent 开发方式，应优先补文档，而不是只留在代码里。
2. 如果新增了 capability agent、workflow 或关键 tool，应补充其职责、输入输出和验证方式说明。
3. 文档应优先描述“为什么存在、谁调用、输入输出是什么、如何验证”，而不是只写实现细节。

---

## 命名与文件约定

1. 规则文件统一命名为 `AGENTS.md`。
2. prompt、schema、workflow、tool 文件命名应体现用途、边界和归属。
3. 不使用含义模糊的文件名，例如：
   - `utils2.py`
   - `temp_agent.py`
   - `new_logic.py`
   - `final_final.py`
4. 测试文件应能直接反映被测对象和场景。

---

## 目标导向

本目录下的工程目标是：

1. 构建业务导向、可复用、可验证的 agent 应用能力
2. 以 OpenAI 官方工作流为主线，减少自定义底层抽象
3. 沉淀清晰的 agent / workflow / tool / prompt / schema 边界
4. 服务当前业务主链路，而不是演化新的通用 AI 平台
