# 文档知识底座持久化复用迭代题目

## 背景

AI 精读工作台不能只把上传文档解析成一次性前端状态，而要把解析结果沉淀成可长期复用的数据资产。用户上传 PDF、DOCX、TXT、MD 或其他学习资料后，系统应完成：

```text
上传资料
  -> 解析与诊断
  -> 统一 DocumentElement / KnowledgeChunk / DocumentAsset
  -> 持久化入库
  -> 工作台刷新恢复
  -> Agent 基于可靠 Chunk 回答
  -> 用户沉淀笔记与学习资产
  -> 后续 OCR / high quality / embedding / 复习持续迭代
```

本题单围绕“可持久化、可复用、可迭代”的数据底座展开，覆盖数据库、后端服务、Agent 上下文、前端恢复、质量诊断、重解析、测试与可观测性。

参考代码：

- `backend/src/main/java/com/personalenglishai/backend/service/translation`
- `backend/src/main/java/com/personalenglishai/backend/controller/translation`
- `backend/src/main/resources/db/schema.sql`
- `backend/src/main/resources/mapper/TranslationDocumentKnowledgeMapper.xml`
- `web/src/api/translation.ts`
- `web/src/pages/app/TranslationWorkspacePage.vue`
- `tasks/6.9/统一文档解析管线与沉浸式翻译IDE题目.md`
- `tasks/6.13/通用资料学习资产类型体系完整实现题目.md`

总体原则：

1. 解析结果必须入库，不能只存在前端内存或接口响应里。
2. Agent 只能依赖统一知识层，不直接依赖 PDFBox、Docling、OCR 等 provider 原始输出。
3. 每个 Chunk、Element、Asset 必须能定位回原文。
4. 数据模型要能支持重解析、版本迭代、OCR 补强和 high quality provider 替换。
5. 前端刷新、重进工作台、切换文档时必须能恢复。
6. 后端接口、Mapper、前端 API 和测试要同步。

## 题目 1：文档知识快照持久化

题目类型：backend + database

难度：困难

### A 小题：设计解析快照主表

#### Prompt

请设计并实现 `translation_document_parse_snapshot` 表，用于保存每篇资料的解析快照、解析状态、质量诊断、语言画像和完整响应 JSON。

#### 难度

偏难

#### 验收标准

- 表包含 `document_id`、`file_name`、`source_type`、`parse_status`、`ocr_status`、`provider`、`parse_mode`。
- 保存 `response_json`、`diagnosis_json`、`quality_json`、`language_profile_json`、`parse_job_json`。
- `document_id` 唯一。
- 支持重复解析时替换旧快照。
- schema 和 migration 都有测试覆盖。

### B 小题：实现解析快照保存与恢复服务

#### Prompt

请实现 `TranslationDocumentKnowledgeStore`，支持保存解析响应，并通过 `documentId` 恢复完整 `TranslationDocumentParseResponse`。

#### 难度

困难

#### 验收标准

- 上传解析完成后自动保存快照。
- `findByDocumentId(documentId)` 能恢复完整响应。
- 序列化失败有明确异常。
- 空 `documentId` 不写入脏数据。
- 有单元测试覆盖保存和读取。

## 题目 2：DocumentElement 行级持久化

题目类型：backend + database

难度：困难

### A 小题：设计文档元素表

#### Prompt

请实现 `translation_document_element` 表，用于保存统一后的文档元素，包括段落、标题、列表、表格和后续图片/公式占位。

#### 难度

偏难

#### 验收标准

- 字段包含 `document_id`、`element_id`、`element_type`、`element_order`、`page_number`、`text`。
- 支持 `bbox`、`provider`、`confidence`、`recognition_status`、`quality_score`、`metadata_json`。
- 建立 `(document_id, page_number, element_order)` 索引。
- `document_id + element_id` 唯一。
- 删除快照时元素可级联删除或有明确清理策略。

### B 小题：实现元素入库映射

#### Prompt

请将 `TranslationDocumentElementDto` 转换为可入库的 Element Record，并通过 MyBatis Mapper 批量或逐条写入。

#### 难度

偏难

#### 验收标准

- 每个解析元素都能保存为独立行。
- 保留 pageNumber、order、type、provider 和 qualityScore。
- metadata 正确序列化。
- 重解析不会保留旧元素。
- 有测试覆盖 Element 保存数量和关键字段。

## 题目 3：KnowledgeChunk 可复用索引

题目类型：backend + RAG data

难度：困难

### A 小题：设计知识 Chunk 表

#### Prompt

请实现 `translation_knowledge_chunk` 表，让 Agent、搜索、复习和学习资产都能复用同一组 Chunk。

#### 难度

困难

#### 验收标准

- 字段包含 `chunk_id`、`chunk_order`、`chunk_type`、`content`、`summary`。
- 保存 `source_element_ids_json`、`page_numbers_json`、`first_page_number`。
- 支持 `section_path_json`、`prev_chunk_id`、`next_chunk_id`、`parent_chunk_id`。
- 建立 `(document_id, first_page_number, chunk_order)` 索引。
- `embedding_status` 字段为后续向量化预留。

### B 小题：实现 Chunk 查询能力

#### Prompt

请实现按 `documentId`、页码、chunkId 查询 KnowledgeChunk 的 Mapper 和 Service 方法，为 Agent 上下文构造做准备。

#### 难度

困难

#### 验收标准

- 可按 `documentId` 获取全部 Chunk。
- 可按页码获取当前页相关 Chunk。
- 可按 chunkId 获取指定 Chunk。
- 查询结果按 chunkOrder 稳定排序。
- 有测试覆盖当前页和前后 Chunk 查询。

## 题目 5：上传解析入库闭环

题目类型：backend

难度：困难

### A 小题：导入链路接入 KnowledgeStore

#### Prompt

请让 `TranslationDocumentImportService` 在解析成功、部分成功或需要 OCR 时，都将知识层数据写入 `TranslationDocumentKnowledgeStore`。

#### 难度

偏难

#### 验收标准

- PDF、DOCX、TXT、MD 导入后都会尝试保存。
- `NEEDS_OCR` 文档也保存诊断和 asset 占位。
- 保存失败不会返回半结构化脏响应。
- 旧的导入 API 返回结构不破坏。
- 有测试覆盖导入后 Store 被调用。

### B 小题：实现按 documentId 读取知识快照接口

#### Prompt

请实现 `GET /api/translation/documents/{documentId}/knowledge`，用于工作台刷新后读取持久化知识快照。

#### 难度

中等偏难

#### 验收标准

- 找到时返回完整 `TranslationDocumentParseResponse`。
- 不存在时返回 404。
- 返回结构和上传导入结果一致。
- 前端 API 提供 `getTranslationDocumentKnowledge(documentId)`。
- 有后端和前端契约测试。

## 题目 6：工作台刷新恢复

题目类型：frontend

难度：偏难

### A 小题：工作台进入时读取持久化知识

#### Prompt

请让翻译/资料工作台在进入页面时优先通过 `documentId` 拉取持久化知识快照，而不是只使用本地 mock 或路由状态。

#### 难度

偏难

#### 验收标准

- 刷新页面后仍能看到文档结构、Chunk、诊断和 Agent 上下文。
- 读取失败时展示可恢复错误状态。
- loading 不阻塞基础布局。
- 不破坏当前 PDF 原文渲染。
- 有前端测试覆盖 API 调用和空状态。

### B 小题：前端状态收敛为单一数据源

#### Prompt

请梳理翻译工作台的数据来源，将解析结果统一收敛到一个 workspace data store 或 composable，避免 props、mock、sessionStorage 多处长期分叉。

#### 难度

困难

#### 验收标准

- 页面核心数据来源清晰。
- mock 数据只作为开发降级，不覆盖真实接口。
- 切换文档时状态正确重置。
- 刷新恢复不依赖旧路由对象。
- 有测试覆盖状态初始化和切换。

## 题目 7：AgentContextBuilder

题目类型：backend + AI integration

难度：困难

### A 小题：构造当前页/当前段落上下文

#### Prompt

请实现 `TranslationAgentContextBuilder`，根据 documentId、pageNumber、elementId 或 chunkId 构造 Agent 可用上下文。

#### 难度

困难

#### 验收标准

- 支持当前 chunk、前后 chunk、当前页 chunk。
- 上下文包含 source refs：pageNumber、chunkId、elementIds。
- 低质量 chunk 可被过滤或降权。
- 上下文长度受控。
- 有测试覆盖不同定位参数。

### B 小题：上下文引用可回跳

#### Prompt

请让 Agent 上下文中的每段材料都保留可回跳引用，前端可根据引用定位到 PDF 页或结构化文本段落。

#### 难度

偏难

#### 验收标准

- 每条 context chunk 有 sourcePage、chunkId、elementIds、excerpt。
- PDF 能跳到页码。
- 精读文本能跳到 element。
- 引用缺失时不传给 Agent 或标记为低可信。
- 有契约测试。

## 题目 10：解析质量诊断与用户决策

- OCR 建议不会打断正常阅读。
