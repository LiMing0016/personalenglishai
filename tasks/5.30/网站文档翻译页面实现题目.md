# 网站文档翻译页面实现题目

## 背景

当前项目已经有独立的翻译页，但 [TranslationPage.vue](F:/personalenglishai/web/src/pages/app/TranslationPage.vue) 仍然偏向普通文本翻译。现有设计稿 [2026-05-23-website-document-translation-design.md](F:/personalenglishai/docs/superpowers/specs/2026-05-23-website-document-translation-design.md) 已经明确了下一步目标：把翻译页升级成“网站文档翻译器”，支持输入 URL、抓取网页正文、清洗非正文内容，并通过 DeepSeek 生成适合学习和复盘的中文 Markdown 文档。

首版范围以“文档整理翻译”为主，重点是：

- 输入网站文档 URL。
- 后端抓取网页正文并清洗结构。
- 调用 DeepSeek 输出结构化学习文档。
- 前端展示摘要、Markdown 正文、分节对照、术语表、学习重点。
- 抓取失败时允许用户粘贴网页正文继续翻译。

本轮不要求：

- 完整网页 UI 覆盖式翻译。
- 浏览器插件方案。
- 登录态网页抓取。
- PDF / Word 文件上传翻译。

建议继续在独立分支完成，不直接在 `main` 上堆叠高风险改动。

## 题目 1：重做翻译页为网站文档翻译工作台

题目类型：feature迭代

难度：中等偏难

### A 小题：重构翻译页输入与状态工作区

#### Prompt

请把当前客户端翻译页从“普通文本翻译”重构为“网站文档翻译工作台”。页面首屏至少包含：

- URL 输入框。
- “整理并翻译”主按钮。
- 当前模式说明，明确是“文档学习模式”。
- 抓取状态区，展示标题、来源 URL、站点名、字数、处理状态。
- 抓取失败时的兜底说明和 `fallbackText` 正文粘贴区。

要求：

1. 不要继续沿用当前左右两栏作文翻译布局。
2. 页面中心应强调“输入网页并整理成学习文档”，不是句子互译。
3. 保留后续“网页对照模式”入口，但只能标记为“后续增强”，不能伪装成已可用。
4. 输入 URL 为空、请求中、失败、成功四种状态要有清晰视觉差异。

#### 难度

中等

#### 验收标准

- 打开 `/app/translation` 后页面主语义变成网站文档翻译。
- 首屏能看到 URL 输入、主按钮、模式说明和抓取状态区。
- 失败态能看到正文粘贴兜底区。
- 不出现“作文翻译”“全文翻译/逐句翻译”这类旧语义。
- 页面在桌面端信息层级清楚，主区域居中，不是简单表单堆叠。

### B 小题：渲染网站文档翻译结果主视图

#### Prompt

请在翻译页实现网站文档结果区。结果区至少包含：

- 文档标题。
- 中文摘要。
- Markdown 风格中文学习文档。
- 分节原文/译文对照。
- 技术术语表。
- 学习重点或 warnings。
- 复制 Markdown 按钮。

要求：

1. 主结果区优先展示 Markdown 学习文档，不要让术语表喧宾夺主。
2. 分节对照应按 section 渲染，而不是把所有内容拼成一段。
3. 术语表必须结构化展示 term、translation、explanation。
4. 复制 Markdown 后给出明确反馈。

#### 难度

中等偏难

#### 验收标准

- 成功响应后能稳定渲染摘要、Markdown、sections、terms、warnings。
- 复制 Markdown 功能可用。
- 术语表和分节对照不是纯 JSON 文本输出。
- 结果区对长文档可滚动，不会压坏输入区。
- 构建通过，页面没有明显文本溢出和布局重叠。

## 题目 2：新增网站文档翻译后端接口与 DTO

题目类型：feature迭代

难度：困难

### A 小题：新增 `/api/translation/web-document` 接口

#### Prompt

请在后端新增网站文档翻译接口：

`POST /api/translation/web-document`

请求体至少包含：

```json
{
  "url": "https://example.com/docs/page",
  "fallbackText": null,
  "targetLanguage": "zh-CN",
  "mode": "study_markdown"
}
```

响应体至少包含：

- `source.url`
- `source.title`
- `source.siteName`
- `source.wordCount`
- `markdown`
- `summary`
- `sections`
- `terms`
- `warnings`

要求：

1. 不要复用现有作文翻译接口。
2. DTO 命名和字段语义要明确体现“web document translation”。
3. `url` 与 `fallbackText` 至少要有一个有效输入。
4. controller 只做参数接收和错误映射，核心逻辑放在 service。

#### 难度

中等偏难

#### 验收标准

- 存在独立的 `POST /api/translation/web-document`。
- 请求和响应 DTO 字段完整、可序列化。
- `url` 为空且 `fallbackText` 为空时返回业务校验错误。
- 不影响现有作文翻译接口。
- 后端分层清晰，没有在 controller 内堆叠抓取与模型逻辑。

### B 小题：前端接入新接口与请求结构

#### Prompt

请在前端新增网站文档翻译 API 调用，不要继续调用现有作文翻译方法。请求中要显式传：

- `url`
- `fallbackText`
- `targetLanguage`
- `mode=study_markdown`

要求：

1. `TranslationPage.vue` 不再调用 `translateEssay`。
2. API 类型定义要覆盖 source、summary、markdown、sections、terms、warnings。
3. 前端错误提示要能区分参数错误、抓取失败、模型失败三类大方向。

#### 难度

中等

#### 验收标准

- 浏览器 Network 中能看到新接口 `/api/translation/web-document`。
- payload 中能看到 `url/fallbackText/targetLanguage/mode`。
- 前端类型定义完整，不靠 `any` 混过去。
- 不再误调用作文翻译接口。

## 题目 3：实现网页正文抓取与 HTML 清洗

题目类型：0-1代码生成（完成）

难度：困难

### A 小题：实现网页抓取与正文提取

#### Prompt

请实现网站文档翻译的网页抓取与正文提取能力。要求后端：

1. 通过 HTTP 获取目标 URL。
2. 限制超时时间和最大响应体大小。
3. 解析 HTML。
4. 优先提取 `article`、`main`、常见文档内容容器。
5. 生成中间结构，至少保留：
   - 标题
   - 段落
   - 列表
   - 代码块
   - 引用块

要求：

1. 这是首版正文提取器，不引入 Playwright。
2. JS 渲染网页抓不到正文时，可以失败并给出可恢复提示。
3. 不要把整页导航、页脚、侧栏原样交给模型。

#### 难度

高

#### 验收标准

- 对常见技术文档页能提取出标题和正文主内容。
- 结果中能区分段落、列表或代码块，而不是纯长文本。
- 抓取超时、403、空页面时能返回明确错误。
- 不依赖浏览器渲染抓取。

### B 小题：实现非正文节点清洗与长度控制

#### Prompt（完成）

请补充网页结构清洗逻辑，重点移除：

- `nav`
- `footer`
- `aside`
- `script`
- `style`
- 广告、目录侧栏、页脚导航等明显非正文内容

同时实现：

1. 内容过短识别。
2. 内容过长截断或分块前处理。
3. 返回 warnings，说明“正文可能不完整”或“内容已截断”。

#### 难度

高

#### 验收标准

- 导航、脚本、样式等非正文节点不会进入模型输入主体。
- 内容明显过短时不会当成成功正文直接翻译。
- 超长网页有截断或分块前控制，不会无限制放大 token。
- warnings 会被带回前端展示。

## 题目 4：接入 DeepSeek 生成结构化学习文档

题目类型：feature迭代

难度：困难

### A 小题：定义 DeepSeek 输出 schema 与翻译 service

#### Prompt

请在后端为网站文档翻译定义结构化输出 schema，并接入 DeepSeek。模型输出至少包含：

- `summary`
- `markdown`
- `sections`
- `terms`
- `warnings`

要求：

1. 输出必须是结构化 JSON，不要只返回自由文本。
2. `sections` 至少包含 `heading/original/translation/notes`。
3. `terms` 至少包含 `term/translation/explanation`。
4. 如果 schema parse 失败，要返回明确错误，不要静默吞掉。
5. 文案目标是“中文学习文档”，不是简单直译。

#### 难度

高

#### 验收标准

- DeepSeek 返回结果能被解析为结构化响应。
- `sections`、`terms`、`summary`、`markdown` 字段都可用。
- schema parse 失败有明确错误信息。
- 后端 service 能区分抓取阶段错误和模型阶段错误。

### B 小题：处理 `fallbackText` 兜底翻译流程

#### Prompt（完成）

请实现 `fallbackText` 兜底流程：当 URL 抓取失败或用户主动粘贴正文时，后端可以直接基于 `fallbackText` 走同一套结构化翻译流程。

要求：

1. `fallbackText` 不依赖 URL 抓取成功。
2. 走同一套 schema 输出，不要额外搞第二种响应格式。
3. 响应中的 `source` 仍要体现当前来源，例如原 URL 或“manual pasted content”。

#### 难度

中等偏难

#### 验收标准

- 抓取失败后，传 `fallbackText` 仍能产出完整结构化翻译结果。
- fallback 流程和 URL 抓取流程返回相同响应结构。
- 不会出现“抓取失败就整体不可用”的死路。

## 题目 5：补齐错误提示、交互反馈和可恢复流程

题目类型：bug修复

难度：中等偏难

### A 小题：把后端错误映射成可理解的前端提示

#### Prompt

请梳理网站文档翻译全链路错误，并在前端给用户展示具体、可恢复的提示，而不是统一“翻译失败，请重试”。至少覆盖：

- URL 格式无效
- 请求超时
- 网站禁止访问
- 内容过短，疑似没有抓到正文
- 内容过长，已截断
- 模型返回格式不完整

要求：

1. 前端提示要给出下一步动作，例如“复制正文到下方继续翻译”。
2. 保留适度技术细节，便于开发排查，但不能把堆栈直接甩给用户。

#### 难度

中等

#### 验收标准

- 不同错误场景下文案有明显区分。
- 用户能看到下一步动作建议。
- 页面不会只剩一个不可操作的红色报错框。

### B 小题：完善加载、复制和重试反馈

#### Prompt

请补齐翻译页交互反馈，包括：

- 抓取中/整理中/翻译中状态
- Markdown 复制成功反馈
- 请求失败后的重试按钮
- fallbackText 提交后的再次翻译反馈

要求：

1. 主按钮在请求中要防重复点击。
2. 长流程中要让用户知道当前卡在抓取还是模型阶段。
3. 失败后不要清空用户已经输入的 URL 或粘贴正文。

#### 难度

中等

#### 验收标准

- 加载态清晰，不会误以为页面无响应。
- 复制有成功反馈。
- 重试不丢失用户输入。
- 请求中按钮状态正确。

## 总体验收标准

完成本题后，应满足以下总体目标：

1. `/app/translation` 已从普通文本翻译页升级为网站文档翻译工作台。
2. 前端调用独立的 `POST /api/translation/web-document`，不再复用作文翻译接口。
3. 后端能抓取并清洗常见网站文档正文，并把结构化内容交给 DeepSeek 生成学习文档。
4. 成功结果能展示：
   - 标题
   - 中文摘要
   - Markdown 学习文档
   - 分节原文/译文
   - 技术术语表
   - warnings / 学习重点
5. URL 抓取失败时，用户可以粘贴网页正文继续翻译，不会被阻断。
6. 错误提示具有定位价值和下一步动作建议。
7. 文档、配置说明、前后端测试和构建验证都有交付。
