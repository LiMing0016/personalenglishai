# 文档治理规则

项目文档的目标是让当前系统行为更容易查找、更容易判断可信度，也更容易随着代码一起维护。

## 文档状态

每篇主文档建议在 frontmatter 中使用以下状态：

| 状态 | 含义 |
| --- | --- |
| `active` | 当前有效，可以作为开发和运行依据。 |
| `draft` | 草稿，尚未成为权威说明。 |
| `deprecated` | 已被替代或不再推荐，但仍有参考价值。 |
| `archived` | 历史材料，不应作为当前依据。 |

## 主文档与归档

主文档至少应该回答下面一个问题：

- 当前产品怎么工作？
- 当前系统怎么设计？
- 哪些接口、字段或行为需要保持兼容？
- 如何启动、部署、测试或排障？
- 为什么做过某个重要技术决策？

任务拆解、Trae 题单和阶段性执行清单放在仓库根目录 `tasks/`，不进入文档站主导航。

归档材料包括已完成的实施计划、旧状态报告、mockup、OCR 提取文件、验收报告和废弃设计。

## 什么时候必须更新文档

改动涉及以下内容时，需要检查并同步更新文档：

- 架构或模块边界。
- API 契约、响应字段或错误码。
- 数据库结构、迁移或持久化行为。
- 部署、本地启动、环境变量或运行手册。
- AI Prompt、评分行为、agent 路由或结构化输出。
- 关键测试、验收或发布流程。

优先维护一篇权威文档，不要让多个相似文档长期并存。过期文档应移动到 `archive/`，或标记为 `deprecated`。

## ADR 规则

当决策影响长期技术方向、依赖、架构、部署、数据模型或 AI 工作流时，应新增 ADR。

模板见 [ADR 模板](./adr/template.md)。
