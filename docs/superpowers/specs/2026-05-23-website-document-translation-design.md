# Website Document Translation Design

## 背景

当前翻译页已经有独立入口，但定位仍偏向普通文本翻译。用户希望它主要用于学习网站文档，例如 OpenAI Developers 文档、技术博客、论文网页和教程页面。目标不是简单翻译一句话，而是把网页中的知识内容整理成可学习、可保存、可复盘的中文学习文档。

## 目标

首版做“网站文档翻译器”：

1. 用户输入网页 URL。
2. 系统自动抓取网页正文。
3. 系统清洗导航、页脚、广告、侧栏等非正文内容。
4. 系统按标题、段落、列表、代码块组织内容。
5. 输出 Markdown 风格的中文学习文档。
6. 保留关键原文对照、术语表、摘要和学习重点。
7. 抓取失败时允许用户粘贴正文继续翻译。

## 首版范围

首版以“方案 B：文档整理翻译”为主。

包含：

- URL 输入和抓取状态展示。
- 网页正文提取。
- Markdown 学习文档生成。
- 原文段落和中文译文对照。
- 技术术语表。
- 学习摘要。
- 抓取失败兜底粘贴。
- 复制 Markdown 结果。

不包含：

- 完整保留原网页 UI 的翻译。
- 浏览器插件式网页覆盖翻译。
- PDF、Word 文件上传翻译。
- 登录态网页抓取。
- 大规模站点爬取。

## 后续增强入口

保留“网页对照模式”的概念，但首版不承诺完整网页 UI 还原。

后续如果要做方案 A，可以分成两类：

1. 应用内网页预览：尝试 iframe 展示原网页，同时在右侧显示中文整理文档。受网站 CSP 和 X-Frame-Options 限制，可能失败。
2. 浏览器扩展：在用户真实浏览器页面上注入翻译层，更接近沉浸式网页翻译体验，但需要单独设计扩展架构。

## 用户流程

```text
进入翻译页
↓
输入网站文档 URL
↓
点击“整理并翻译”
↓
后端抓取网页
↓
提取正文结构
↓
模型生成学习文档
↓
前端显示：
  - 文档标题
  - 中文摘要
  - 分节翻译
  - 关键术语
  - 学习重点
  - Markdown 复制按钮
```

失败流程：

```text
URL 抓取失败
↓
展示失败原因
↓
显示“粘贴网页正文继续”
↓
用户粘贴正文
↓
走同一套整理翻译流程
```

## 前端设计

翻译页从普通左右文本框升级为文档翻译工作台。

主要区域：

- 顶部：URL 输入框、模式说明、开始按钮。
- 左侧或上方：抓取到的网页信息，包括标题、来源 URL、字数、抓取状态。
- 主区域：Markdown 风格中文学习文档。
- 辅助区域：术语表、学习重点、复制按钮。
- 失败兜底区：正文粘贴框。

首版默认模式为“文档学习模式”。页面可以展示“网页对照模式”入口，但标记为后续增强，避免用户误以为已经支持完整网页 UI 翻译。

## 后端设计

新增网站文档翻译接口，避免复用现有作文翻译接口造成语义混乱。

建议接口：

```http
POST /api/translation/web-document
```

请求结构：

```json
{
  "url": "https://example.com/docs/page",
  "fallbackText": null,
  "targetLanguage": "zh-CN",
  "mode": "study_markdown"
}
```

响应结构：

```json
{
  "source": {
    "url": "https://example.com/docs/page",
    "title": "Document title",
    "siteName": "Example Docs",
    "wordCount": 1200
  },
  "markdown": "# 中文学习文档...",
  "summary": "这篇文档主要讲...",
  "sections": [
    {
      "heading": "Original heading",
      "original": "Original paragraph...",
      "translation": "中文翻译...",
      "notes": ["学习提示"]
    }
  ],
  "terms": [
    {
      "term": "Structured Outputs",
      "translation": "结构化输出",
      "explanation": "让模型输出符合 schema 的结构化数据。"
    }
  ],
  "warnings": []
}
```

## 网页正文提取

首版采用后端 HTTP 抓取 HTML，再用正文提取策略清洗内容。

推荐顺序：

1. 请求 URL，限制超时时间和最大响应体大小。
2. 解析 HTML。
3. 优先提取 `article`、`main`、文档内容容器。
4. 移除 `nav`、`footer`、`aside`、`script`、`style` 等非正文节点。
5. 保留标题、段落、列表、代码块、引用块。
6. 转成中间结构，再交给模型整理翻译。

如果网页需要 JS 渲染，首版可以失败并提示用户粘贴正文，不引入 Playwright 抓取，降低部署复杂度。

## 模型输出要求

模型应输出结构化结果，而不是只输出一段自由文本。

建议后端使用 Pydantic 或 JSON Schema 约束：

- `summary`: 中文摘要。
- `markdown`: 可复制的完整 Markdown 学习文档。
- `sections`: 分节原文和译文。
- `terms`: 术语表。
- `warnings`: 低置信度或抓取不完整提示。

这样前端既能渲染完整 Markdown，也能单独展示术语表和学习重点。

## 错误处理

需要覆盖以下错误：

- URL 格式无效。
- 请求超时。
- 网站禁止访问。
- 内容过短，疑似没有抓到正文。
- 内容过长，需要截断或分块。
- 模型返回格式不完整。

错误提示要给用户下一步动作，例如“复制正文到下方继续翻译”。

## 测试

后端测试：

- URL 校验。
- HTML 正文提取。
- 导航和脚本清洗。
- fallbackText 兜底流程。
- 结构化响应解析。

前端测试：

- URL 输入后按钮状态正确。
- 成功结果渲染 Markdown、摘要、术语表。
- 抓取失败时显示粘贴正文入口。
- 复制 Markdown 正常。

构建验证：

```bash
npm run build
```

后端验证按实际模块选择 Maven 测试范围。

## 合并判断

这个需求涉及新的页面能力、后端接口和 AI 输出结构，建议继续在 `codex/translation-page` 独立分支开发。完成首版并通过前后端验证后，再评估是否合并到 `main`。
