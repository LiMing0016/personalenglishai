# 写作页手写作文图片导入设计稿

## 1. 目标

在现有写作页中增加一个低打扰的“手写作文图片导入”能力。

用户可以在写作过程中：

- 从右上角 `...` 更多菜单中发起上传
- 选择一张手写英文作文图片
- 由后端调用现有 AI 多模态能力完成识别
- 在结果确认后，将识别文本导入当前写作区

该能力的目标不是做一个完整 OCR 平台，而是为现有写作主链路提供一个新的输入入口。

## 2. 范围

### 2.1 第一版纳入范围

- 只支持单张图片上传
- 支持常见图片格式，如 `jpg / jpeg / png / heic`
- 支持手写英文作文识别
- 支持识别结果预览
- 支持用户选择：
  - `替换写作区`
  - `追加到写作区`
- 识别成功后，将当前图片来源与识别文本绑定到当前写作文档

### 2.2 第一版不纳入范围

- 不支持 PDF
- 不支持网页直接调起摄像头
- 不支持多张图片批量识别
- 不支持复杂版面还原
- 不支持识别历史列表
- 不支持逐行定位或图文坐标映射
- 不支持独立的手写作文管理页

## 3. 产品定义

### 3.1 功能定位

该功能是“写作内容导入器”，不是“新建题目入口”，也不是“右侧持续面板工具”。

它服务于当前写作上下文，核心作用是把纸面手写内容转为当前编辑器中的可编辑文本。

### 3.2 入口位置

入口放在写作页右上角 `...` 更多菜单中。

新增菜单项：

- `上传手写作文`

这样可以保持主界面简洁，不打断常用提交、清空和导航操作，也符合该功能“低频但重要”的定位。

## 4. 用户流程

### 4.1 标准流程

1. 用户打开写作页
2. 用户点击右上角 `...`
3. 用户点击 `上传手写作文`
4. 系统弹出独立导入弹层
5. 用户选择一张图片
6. 系统展示图片预览，并允许用户点击 `开始识别`
7. 后端完成识别后，弹层展示：
   - 原图预览
   - 识别结果文本
8. 用户选择：
   - `替换写作区`
   - `追加到写作区`
9. 系统将文本导入当前编辑器，并把图片来源与识别结果绑定到当前文档

### 4.2 非空写作区保护

当写作区已有内容时，系统不能自动覆盖。

必须要求用户在识别结果态显式选择：

- `替换写作区`
- `追加到写作区`

系统不提供“识别完成即自动导入”的默认行为。

### 4.3 单任务限制

第一版一次只允许处理一个识别任务。

在识别进行中：

- 不允许再次触发新的图片上传
- 不允许并发识别多个任务

这样可以避免当前写作区、当前文档元数据和识别弹层之间出现状态冲突。

## 5. 交互设计

### 5.1 弹层结构

推荐使用独立弹层组件，不直接把上传和识别逻辑塞进 `EditorShell` 主文件。

弹层分为三个状态：

#### 状态 A：初始态

- 文件选择按钮
- 支持格式说明
- 关闭按钮

#### 状态 B：识别中

- 图片预览
- `识别中` loading
- 处理中提示文案

#### 状态 C：识别结果态

- 左侧原图预览
- 右侧识别文本结果
- 底部操作按钮：
  - `替换写作区`
  - `追加到写作区`
  - `取消`

### 5.2 结果展示原则

识别结果展示以“可导入文本”为主，不展示复杂诊断信息。

第一版重点是：

- 让用户快速看见识别文本
- 让用户快速决定如何导入

若需要保留原始识别文本和归一化文本的差异，应保留在后端响应中，而不是在 UI 上同时展示两套文本。

## 6. 前端架构设计

### 6.1 推荐接入方式

采用“`EditorShell` 触发 + 独立组件承载”的方案。

建议新增组件：

- `HandwritingImportDialog.vue`

`EditorShell` 只负责：

- 打开弹层
- 关闭弹层
- 接收导入结果
- 把文本写入现有草稿状态

独立组件负责：

- 选图
- 预览
- 调识别接口
- 展示识别状态
- 处理替换/追加确认

### 6.2 状态边界

需要明确区分两类状态：

#### 临时 UI 状态

存在于导入弹层内：

- 当前选择的文件
- 当前本地预览图
- 上传中状态
- 识别中状态
- 识别失败状态
- 识别结果文本

#### 当前文档持久化元数据

存在于当前写作文档对应的后端记录中：

- 手写来源图片地址
- 手写来源类型
- 最近一次识别文本
- 导入时间

### 6.3 不新增第二套草稿真源

识别结果一旦用户点击导入：

- 仍然只写入当前 `draftStore.draftText`
- 不应额外创建另一套并行“识别草稿 store”

这样可以保持现有写作主链路的单一真源。

## 7. 后端架构设计

### 7.1 功能边界

后端新增一个独立识别接口，用于接收图片并调用现有 AI 多模态能力。

后端职责包括：

- 接收上传图片
- 基础格式校验
- 调用多模态 AI 识别手写英文作文
- 返回识别结果
- 在用户确认导入后，保存当前文档关联的手写来源元数据

### 7.2 识别策略

第一版采用方案 A：

- 直接使用当前项目现有 AI provider 能力
- 不新接 OCR 服务
- 不依赖 Python agent 项目

Prompt 应严格限制输出：

- 只提取作文正文
- 尽量保留段落
- 不补写不存在的内容
- 不输出解释、分析、标题或 markdown

### 7.3 返回结构

后端建议返回结构化结果：

```json
{
  "imageUrl": "https://...",
  "recognizedText": "原始识别文本",
  "normalizedText": "可直接导入编辑器的文本",
  "confidence": 0.86
}
```

其中：

- `recognizedText` 用于保留原始识别结果
- `normalizedText` 用于真正导入写作区
- `imageUrl` 用于当前文档回看来源图

## 8. 文档绑定设计

### 8.1 绑定目标

第一版不做识别历史表，不做多次版本追踪。

只保留“当前文档最近一次手写导入来源”。

### 8.2 建议字段

建议在当前文档对应元数据上增加以下信息：

- `handwritten_source_type`
- `handwritten_source_image_url`
- `handwritten_recognized_text`
- `handwritten_imported_at`

其中：

- `handwritten_source_type` 第一版固定为 `image`
- `handwritten_recognized_text` 保存最近一次已确认导入时对应的识别文本

### 8.3 绑定时机

不是“识别成功即落库”，而是“用户确认导入后再绑定到当前文档”。

原因：

- 识别成功不代表用户接受该结果
- 用户可能识别后直接取消
- 只有真正导入写作区，才应视为一次有效的手写来源绑定

## 9. 导入规则

### 9.1 替换写作区

用户选择 `替换写作区` 时：

- 用 `normalizedText` 替换当前全部草稿内容
- 保持后续本地持久化和刷新恢复逻辑不变

### 9.2 追加到写作区

用户选择 `追加到写作区` 时：

- 将 `normalizedText` 追加到现有草稿末尾
- 需要自动处理必要的段落分隔

### 9.3 导入后行为

导入完成后：

- 编辑器内容更新
- 当前草稿持久化逻辑继续生效
- 后续评分、语法、润色链路按现有逻辑运行

第一版不要求导入后立刻自动触发评分。

## 10. 错误处理

第一版至少覆盖以下错误：

- 图片格式不支持
- 图片过大
- 上传失败
- 识别失败
- 识别结果为空
- 用户主动取消

错误处理目标是：

- 不污染当前写作区
- 不清空已有草稿
- 不写入无效文档关联元数据

## 11. 对现有主链路的约束

该功能必须遵守以下边界：

- 不新增写作页第二套核心草稿状态
- 不改写现有评分提交协议
- 不侵入右侧面板体系
- 不影响考试模式与自由模式现有编辑行为
- 不破坏当前草稿刷新恢复逻辑

## 12. 测试重点

### 12.1 前端回归

- 空白写作区导入成功
- 非空写作区选择替换
- 非空写作区选择追加
- 识别失败后不污染草稿
- 考试模式下可正常导入
- 自由模式下可正常导入

### 12.2 后端回归

- 图片格式校验
- 多模态识别接口成功返回
- 空结果处理
- 绑定当前文档手写来源元数据

### 12.3 持久化回归

- 导入后刷新页面，草稿内容仍然存在
- 当前文档的手写来源元数据可重新读取

## 13. 推荐实施顺序

1. 新增前端弹层组件和入口
2. 打通后端识别接口
3. 打通识别结果导入写作区
4. 增加当前文档手写来源元数据绑定
5. 做刷新恢复与错误回归

## 14. 结论

该功能应以“现有写作页中的单次导入能力”落地，而不是发展为新的 OCR 子系统。

采用方案 2 的原因是：

- 能控制 `EditorShell` 的复杂度
- 前端边界清楚
- 便于后续扩展“查看原图”或“重新识别”
- 不需要等待 Python agent 项目即可独立交付
