# 个人中心头像上传规格

## 背景

个人中心已经展示用户昵称首字母头像，`users` 表和个人资料接口也已经包含
`avatar_url` 字段，但当前头像按钮仍用于编辑昵称，用户无法上传或展示自己的头像。

本需求在现有个人中心重设计分支中补齐头像上传能力。第一版优先形成完整、可验证的
上传链路，不引入图片裁剪组件或新的对象存储依赖。

## 目标

1. 用户可以在个人中心点击头像选择并上传图片。
2. 上传成功后立即展示新头像，刷新页面后仍然保留。
3. 文件校验、存储路径和数据库更新均由后端统一控制。
4. 保持接口契约稳定，使本地文件存储后续可以平滑替换为对象存储。

## 非目标

- 第一版不提供裁剪、旋转、滤镜或缩放编辑器。
- 不支持 GIF、SVG、HEIC 等其他格式。
- 不在上传请求中同步删除旧头像文件。
- 不新增前端组件库、状态库或图片处理依赖。

## 交互设计

个人中心头部继续使用当前圆形头像样式：

- 没有头像时显示昵称或邮箱首字母。
- 有头像时使用圆形裁切展示图片。
- 鼠标悬停或键盘聚焦时显示相机图标和“更换头像”提示。
- 点击头像打开系统文件选择器，接受 JPG、PNG 和 WebP。
- 选择文件后立即开始上传；上传期间显示加载状态并禁止重复触发。
- 上传成功后直接替换当前头像并提示“头像已更新”。
- 图片加载失败时回退到首字母头像，不显示破损图片。
- 文件不合规或接口失败时保留原头像，并显示明确错误提示。

昵称仍然只通过昵称右侧的铅笔按钮编辑，头像点击不再触发昵称编辑。

## 文件约束

- 支持的 MIME 类型：`image/jpeg`、`image/png`、`image/webp`。
- 单文件最大 5 MiB。
- 每次请求只能上传一个文件。
- 后端不能信任客户端文件名或单独依赖请求声明的 MIME 类型。
- 后端通过文件头识别实际图片类型；声明类型和实际类型不匹配时拒绝上传。
- 存储扩展名由实际图片类型决定，不使用用户原始扩展名。

## API 契约

### 上传头像

`POST /api/users/me/profile/avatar`

请求：

- 需要当前 JWT 鉴权。
- `Content-Type: multipart/form-data`
- 表单字段：`file`

成功响应：

```json
{
  "code": "0",
  "message": "success",
  "data": {
    "avatarUrl": "/uploads/avatars/42/7c50fb2d-32d7-48d4-aee9-44f8b564124c.webp"
  }
}
```

失败场景：

- 文件为空：返回参数校验错误。
- 文件超过 5 MiB：返回参数校验错误。
- 声明格式或实际文件格式不支持：返回参数校验错误。
- 用户不存在：返回用户不存在错误。
- 文件写入失败：返回通用服务错误，不更新数据库。
- 数据库更新失败：返回通用服务错误，不返回成功地址。

现有 `GET /api/users/me/profile` 继续通过 `avatarUrl` 返回当前头像地址，不改变其他字段。

## 后端设计

新增头像存储服务，职责保持单一：

1. 校验文件大小和实际图片类型。
2. 生成不可预测的随机文件名。
3. 将文件写入配置的上传根目录下
   `avatars/{userId}/{uuid}.{ext}`。
4. 返回以现有公开路径为前缀的相对 URL。

控制器只接收鉴权用户和 Multipart 文件，并调用服务。服务保存成功后通过
`UserMapper` 更新 `users.avatar_url`。路径使用规范化后的上传根目录解析，并校验目标
路径仍位于该根目录内，避免路径穿越。

存储配置复用：

- `app.upload-dir`：本地上传根目录，默认 `uploads`。
- `app.upload-public-path`：公开访问前缀，默认 `/uploads`。
- 现有 `WebConfig` 继续暴露 `/uploads/**`。

第一版不在同步上传流程中删除旧头像。这样可以避免文件已删除但数据库事务失败造成的
破损头像，也不会误删未来由对象存储托管的地址。旧文件清理作为独立运维任务处理。

## 前端设计

`userApi` 新增 `uploadAvatar(file)`，通过 `FormData` 调用上传接口并返回
`avatarUrl`。

个人中心页面只维护本次上传的临时状态：

- 隐藏的文件输入；
- 是否正在上传；
- 图片加载是否失败。

服务端个人资料仍然是头像地址的唯一数据源。上传成功后将响应中的 `avatarUrl`
写回当前资料对象；重新进入页面时仍由 `getMyProfile()` 获取，不新增 Pinia store 或
浏览器存储。

前端在发起请求前检查格式和 5 MiB 大小，以便及时反馈；后端重复校验并作为最终安全
边界。

## 错误处理

- 格式不支持：提示“请选择 JPG、PNG 或 WebP 图片”。
- 文件过大：提示“头像不能超过 5MB”。
- 上传失败：提示“头像上传失败，请稍后重试”。
- 图片加载失败：静默回退到首字母头像。
- 重新选择同一个文件时也应触发上传，因此每次处理后清空文件输入值。

任何失败都不得覆盖当前页面中的原头像地址。

## 测试设计

后端测试：

- 合法 JPEG、PNG、WebP 文件能够保存并更新头像地址。
- 空文件、超大文件、伪造 MIME 类型和不支持的文件头被拒绝。
- 生成路径位于配置的头像目录，且不使用原始文件名。
- 文件写入失败时不更新数据库。
- 控制器从鉴权上下文取得用户 ID，并返回结构化头像地址。

前端测试：

- 允许的格式和大小能够通过预校验。
- 不支持格式和超过 5 MiB 的文件返回对应错误。
- 上传 API 使用 `file` 字段构造 `FormData`。
- 有头像时渲染图片，无头像或加载失败时渲染首字母。
- 点击头像触发文件选择而不是昵称编辑。

验收：

1. 登录后打开 `/app/me?tab=overview`。
2. 点击头像，选择合法图片。
3. 上传期间只能提交一次，成功后页面立即显示新头像。
4. 刷新页面，新头像仍然显示。
5. 分别选择超大文件和不支持格式，原头像保持不变并出现正确提示。
6. 键盘可以聚焦头像并打开文件选择器。

## 兼容性与部署

本功能不修改数据库结构；`users.avatar_url` 已存在。Vite 已代理 `/uploads` 到后端，
本地开发无需新增代理。生产环境需要继续保证网关或后端对 `/uploads/**` 的访问配置
可用。

未来迁移对象存储时，保留上传接口和 `avatarUrl` 响应字段，只替换头像存储服务的
写入实现和返回地址。
